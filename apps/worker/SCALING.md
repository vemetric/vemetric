# Concurrent ingestion rollout

Device and session jobs no longer have a global concurrency limit. Device workers use a shared Redis success cache; session workers merge current state in Redis and one active scheduled worker writes batches of versioned snapshots. Event workers retain their existing insert behavior.

The replacement tables are `session_v3` and `device_v2`; `session` and `device` remain for reconciliation and are deleted only in a separate, later step. The session schema retains the existing column types and defaults, including `referrerUrl DEFAULT referrer`, `referrerType DEFAULT 'unknown'`, and an empty-string default for `queryParams`; deletion uses an `Int8 deleted` flag as the tombstone marker. Historical migration 11's `session_v2` name is not reused.

## Deployment order

1. Provision Redis headroom for the backlog plus pending session state. Configure `maxmemory-policy noeviction` and persistence. Local Compose preserves AOF with Redis's default `appendfsync everysec`, which can lose roughly one second of recent writes after a crash. Stronger crash durability is a separate decision that requires throughput benchmarks. Verify the production persistence and failover guarantees separately; asynchronous replica failover is not made lossless by this code. Do not use a cache eviction policy for this Redis instance.
2. Globally pause the processing queues using BullMQ `Queue.pause()` (Bullboard's queue pause action), then gracefully stop **every** old worker replica. A global pause survives restarts; a worker-local pause does not. Wait until active jobs finish and all replicas have stopped, allowing sufficient platform termination grace time. Stop standalone imports and migration writers too. Keep Redis and hubs running and leave waiting, delayed, and failed jobs intact. Hubs can continue enqueueing while Redis has capacity. Do not run old and new processors concurrently.
3. Verify the existing session table uses `ReplacingMergeTree(endedAt)` and the device table uses `CollapsingMergeTree(sign)`. Rehearse against a production-sized copy first, with enough ClickHouse disk space for both copies and Redis memory for the measured backlog. Apply `15_concurrent_ingestion.sql`: it **only creates `session_v3` and `device_v2`**. Historical migration 14 is already documented as skipped on production; do not blindly reapply it.
4. With all ClickHouse writers still stopped, run the separate backfill command below, using **one operator/process**. It reports each project/table, copies missing logical rows, and compares full rows in both directions before reporting completion. Manually confirm the command exits successfully and reports `Backfill complete. Both tables verified.` before restarting any writer. Backfill and verification duration must fit the maintenance window and Redis capacity.
5. Deploy the new hub, application and Bullboard builds, then start the new workers while queues remain globally paused. New application reads need the completed backfill too. Backfill completion is a manual deployment prerequisite; workers do not check or store a completion flag. Device/session workers still check Redis connectivity and table existence, which does not verify the backfill. Device/session worker initialization then removes their persisted global concurrency caps. Old hub/Bullboard modules can reapply the old caps on import, so replace all old replicas.
6. Resume ingestion queues and `session-flush`, with at least one flusher replica running. Keep `merge-user` paused until the ingestion backlog catches up, so the five-minute session-readiness deadline is not consumed by the maintenance backlog. Then resume merges and other paused queues. Verify caps with BullMQ `getGlobalConcurrency()`, inspect failed/stalled jobs, confirm pending session revisions drain, and compare session/device metrics before increasing concurrency.

### Separate backfill command

From the repository root, with production `CLICKHOUSE_HOST`, `CLICKHOUSE_DB`, `CLICKHOUSE_USER`, and `CLICKHOUSE_PASSWORD` supplied by your deployment environment:

```sh
bun run --cwd packages/clickhouse backfill-ingestion --writers-stopped
```

For local rehearsals, `backfill-ingestion-local` loads the root `.env` instead. The migration CLI uses **`CH_MIGRATIONS_*`** environment variables; the backfill uses the application's **`CLICKHOUSE_*`** variables. Ensure both point to the same database. `--writers-stopped` is an operator assertion, not an automated shutdown or distributed lock. It cannot detect legacy workers or external imports: keep queues paused and run only one backfill process. The command's per-query client timeout defaults to one hour (`INGESTION_BACKFILL_TIMEOUT_MS`); server/proxy timeouts still apply.

If a run fails or is interrupted, keep writers stopped and rerun the same command. First ensure the previous process and its server-side queries have ended; a disconnected request may still be executing in ClickHouse (`system.processes`). Existing rows are retained and only missing rows are copied. Verification includes keys, all values, nullable fields and revision/deletion metadata, including unexpected target-only projects. The command reports completion only after all verification succeeds. If that final output is lost, rerun while all writers remain stopped to verify again. For the legacy session snapshot, whole-row selection preserves NULL values and resolves equal-time candidates consistently after legacy `FINAL`; devices retain their earliest surviving creation after collapsing cancelled rows. Deleted sessions, empty session IDs, and collapsed devices are excluded, matching the previous backfill's logical eligibility.

If verification fails, investigate the named project/table and unexpected target rows before retrying; never truncate a target that has received live writes. Do not run the backfill again after new ingestion writes have started: it copies a legacy snapshot and is only intended for the stopped-writer migration window. There is no persistent completion flag or automatic startup gate; confirming completion and starting workers in the correct order are manual deployment steps.

Every worker replica runs all workers; scale the deployment horizontally instead of splitting roles. User creation/update remain globally serialized; rare identity merges are also globally serialized. More event concurrency does not change the existing event retry/deduplication semantics. The user-list query cancels events within each owner before selecting users, so cancelled source rows cannot select the old owner while background merges are pending. This release does not claim exactly-once event ingestion; event retry/deduplication remains a separate concern.

## State and recovery

With `AXIOM_TOKEN` configured, every worker exports job counters and durations, including `session-flush`. Queue counts (`bullmq.queue.jobs`) cover the entire queue, so they are recorded by a single scheduled job on the internal `bullmq-metrics` queue. BullMQ global concurrency 1 plus one job scheduler guarantees exactly one replica records them per interval, with automatic failover and no per-instance configuration. That recorder polls all queues, including `session-flush`, and excludes its own queue. The metrics queue is otherwise inert and needs no capacity planning. Job counters can be aggregated across workers.

- Device IDs are unchanged. `device_v2` replaces rows by `(projectId,userId,id)`. Live revisions favor the earliest creation timestamp; the highest UInt64 revision is reserved for a tombstone. The shared `vm:device-written:*` marker expires after 15 minutes by default (`DEVICE_CACHE_TTL_SECONDS`) and is written only after ClickHouse acknowledges an insert; it is a simple existence marker, and the device creation timestamp is derived by the model at insert time. Duplicate cache misses are harmless to the logical device view because device_v2 resolves them by revision. Device writes use ClickHouse async inserts with a 100 ms batch window and `wait_for_async_insert=1`; cache markers and job completion still wait for persistence. Set `DEVICE_ASYNC_INSERTS=false` to disable this batching during comparison tests.
- Session state is keyed by `(projectId,id)` and has a monotonically increasing revision. Redis CAS commits state, its dirty marker and pending-user index together. Conflicts are retried from current state. Session activity can arrive out of order; page-leave before creation is buffered only in Redis on a best-effort basis, with the same five-minute TTL as clean state. `startedAt` is immutable once a session snapshot exists: a late earlier event corrects entry metadata but never the start time or its partition. Location fields fill only while missing: a delayed event never replaces an existing location. Session merges preserve the target session's known location fields and fill its missing fields from the source, and keep the target's start. No per-field location timestamps are stored.
- The flusher runs every second with BullMQ global concurrency 1, writing up to 500 sessions per batch and up to ten batches per tick. Multiple worker replicas provide failover, while only one scheduled flush job runs at a time. There are no per-session claims or leases. Markers stay pending until the exact snapshot is acknowledged. A resumed stalled job is safe because ClickHouse selects the highest revision and Redis only clears unchanged snapshots. Continuously updated sessions move behind other waiting sessions after a successful write, preventing starvation.
- Session snapshots contain no duplicate JSON payload. Cache hydration reads the existing session columns, revision and deletion marker. Entry metadata uses the fixed `startedAt` as its comparison point. Events at or after that time keep existing metadata; events before it can replace metadata in processing order. This intentionally favors simpler state over exact earliest-event attribution. Ownership and profile values use only the existing `userId`, `userIdentifier` and `userDisplayName` columns.
- Only an acknowledged, unchanged revision becomes clean. Clean Redis state expires after five minutes by default (`SESSION_STATE_CACHE_TTL_SECONDS`). Early activity without an initialized session uses the same TTL from its latest buffered change, has no dirty marker, and is never flushed to ClickHouse. If it expires before creation arrives, that activity timestamp is lost; creation still proceeds normally. Initialization removes the TTL and queues the combined state for flushing. Initialized dirty state and deletion tombstones have no TTL until successfully flushed. Cache misses hydrate the last persisted state and revision. Failed writes remain dirty and retry on subsequent ticks. Never manually expire, delete or flush dirty state.
- Production reads use the shared `currentSessionRows` and `currentDeviceRows` SQL helpers, with no database views or `FINAL`. They resolve values with `argMax(tuple(column), revision).1`, preserving nullable values; retries of a revision must contain the same snapshot. The helper owns all immutable scan scoping (`projectId`, `id`) and the optional `startedAt` bounds, so date-limited queries prune partitions instead of aggregating the project's full history and callers do not repeat those predicates; inside the helper `startedAt` must be qualified with the table name because the select list aliases it. Outer queries only filter resolved values (owner, location, source, duration, filter config); deletion is handled by the helper's `HAVING deleted = 0`. Unused column aggregates are pruned by ClickHouse. `session_v3` is partitioned by `toYYYYMM(startedAt)`: the start is immutable once a session snapshot exists (a late earlier event corrects entry metadata but never the start), so all revisions of an initialized session share one partition and replacement stays within it. Session cache hydration instead reads one key ordered by revision descending, including deleted snapshots. The separate one-time legacy backfill uses `FINAL` to resolve legacy session replacement keys and cancelled device rows before selecting the snapshot. Per-user reads (`findByUserId`, `findLatestByUserId`) are two-phase because `session_v3` is ordered `(projectId, id)` and a session's userId is mutable: they first collect candidate ids (`WHERE projectId AND userId`, pruned by the `user_id_idx` bloom-filter skip index so this is not a project scan) and then resolve the latest revision through `currentSessionRows`, which drops entries no longer owned by the user or tombstoned. **Rollout gate:** benchmark read latency and memory on production-sized data (especially the per-user two-phase reads and the merge path) before rollout; do not deploy on synthetic-size confidence alone.
- Session ownership changes and source tombstones use the same atomic commit as tracking updates. These tombstones also reject concurrent writes of those same source keys. A tombstone is a row with `deleted = 1`. Tombstones are durable and are deliberately **not** expired by a table TTL: removing only the marker row while an older live revision still exists would resurrect the key. They are written compact (project, key, partition anchor, revision, `deleted`) so their storage stays small, and live rows keep `deleted = 0`. Because there is no automatic expiry, a late write of a merged-away key is rejected indefinitely and manual recovery must remove the tombstone explicitly. Monitor `SELECT count() FROM session_v3 WHERE deleted = 1` (and the same for `device_v2`) and revisit cleanup only if it grows.
- The merge worker moves only sessions already found for the old user. An event may reference a historical session that never existed; that event still migrates with its original session ID, as it did before this refactor. If Redis contains an empty initialization placeholder or early activity for an event's session ID, the merge postpones the same BullMQ job for five seconds using `moveToDelayed` and `DelayedError` so an active session job can finish. The first wait timestamp survives retries. After five minutes, a still-uninitialized placeholder is skipped and the merge continues with available sessions and events. A session job that has not started has no Redis marker and retains the pre-existing late-job race. Ownership changes still check initialization inside the Redis CAS loop; neither session completion nor ClickHouse flushing is required for a session already present in the snapshot.
- `createOrExtend` continues to carry event enrichment data. `extend` only advances activity time and can be used by a future heartbeat; it buffers the timestamp for up to five minutes by default if enrichment has not arrived yet. This change does not add a heartbeat producer.
- User and session redirection are deferred identity work; no redirect mapping is stored in ClickHouse or Redis. This rollout explicitly accepts that a late `createOrExtend` or `extend` job for a tombstoned source session completes without recreating that session or extending the destination, including after the Redis cache expires and the tombstone is loaded from ClickHouse. A new session/device key arriving after the merge's scan can still belong to the old user; event jobs retain their queued user ID. This release does not claim comprehensive late-job attribution.
- The synchronous `persistSessionUpdates()` API in the worker ingestion module performs a bounded flush for immediate query visibility. Importers pass `{ preserveDuration: true }` to retain measured duration values on insert; other callers derive duration from session activity. Both paths use the same revision and conditional-acknowledgement protocol, so overlap with the scheduled worker is safe. Import tooling needs `REDIS_URL` and the migration-15 tables; `pirsch-data-import` and `seed-local-random-user` assert this up front via `assertIngestionStateStorage()` and close the shared Redis client on exit.
- Enqueue failures continue to be stored in PostgreSQL using the existing fallback. Automatic recovery of those records is outside this refactor; existing manual recovery procedures still apply.
- Exhausted BullMQ retries remain failed jobs and require monitoring/retry. The former `SKIP_ENRICHMENT_PROJECT_IDS` bypass is no longer used by device/session workers.

Track queue age (including the `session-flush` scheduler queue, which grows if a flush exceeds its 1s interval) and failed/stalled jobs, `ZCARD vm:{session-state}:dirty`, the oldest pending timestamp, Redis memory/persistence health, and ClickHouse insert failures/parts/read latency. Cached device hits do not reduce insert volume for entirely new bot identities; measure that workload separately.

## Code responsibilities

- `packages/clickhouse/src/models/session.ts` and `models/device.ts`: model-derived column selectors and revision selection for analytics, lookups and joins; `clickhouseSession` also exposes raw revision reads and batch inserts.
- `apps/worker/src/ingestion/session-state.ts`: pure TypeScript session calculations.
- `apps/worker/src/ingestion/session-buffer.ts`: update and existing session-merge orchestration.
- `apps/worker/src/ingestion/session-store.ts`: typed storage operations, cache hydration and pending snapshots.
- `apps/worker/src/ingestion/session-flush.ts`: ClickHouse batch writes and conditional acknowledgement.
- `apps/worker/src/ingestion/session-redis-commands.ts`: small named atomic commands registered with ioredis `defineCommand`; no session business rules.

## Rollback

Keep the legacy tables until reconciliation is complete. Before any new writes, restarting the old build remains possible; if legacy writes resume, the copied snapshot is stale and must be rebuilt and reverified before a later cutover. After new writes, stop producers/processors as appropriate, flush and verify all pending session state, and export the current logical state into freshly rebuilt legacy tables using their original schemas. Simply starting the old build would hide all writes made only to the new tables. Prefer a forward fix once ingestion has switched. Never drop the new tables or Redis state as a rollback shortcut.

## Validation

The database-backed tests require a disposable migrated ClickHouse database named `vm_concurrency_test_*`, a disposable PostgreSQL database of the same naming pattern, and a dedicated Redis on port 16389. They clear test state; never point them at production.

```sh
INGESTION_STATE_TESTS=1 bun run --cwd apps/worker test -- tests/ingestion-state.integration.test.ts
INGESTION_STATE_TESTS=1 bun run --cwd packages/clickhouse test -- tests/ingestion-backfill.integration.test.ts
INGESTION_STATE_TESTS=1 bun run --cwd apps/worker test -- tests/session-flush.integration.test.ts
INGESTION_STATE_TESTS=1 bun run --cwd apps/worker test -- tests/merge-user-delay.integration.test.ts
bun run --cwd apps/hub test:integration
bun run tsc
bun lint
```

Pass explicit `CLICKHOUSE_DB`, `CLICKHOUSE_HOST`, `CLICKHOUSE_USER`, `CLICKHOUSE_PASSWORD`, `DATABASE_URL` and `REDIS_URL` for the disposable services. Tests cover concurrent assignment/updates, duplicate inserts, early page-leave, cache rehydration, updates during a flush, lost acknowledgements, bounded batches, single-flusher scheduling across replicas, resumed stale flushers, fairness under continuous updates, month boundaries, ownership changes and source tombstones after session merges. These are correctness tests, not a production throughput benchmark.
